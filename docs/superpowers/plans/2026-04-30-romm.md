# RomM (ROM Library Manager) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deploy RomM into the existing `games` namespace, exposed at `https://romm.${SECRET_DOMAIN}` over the internal envoy gateway, backed by a 1-instance CNPG postgres cluster, an embedded Valkey cache, a 5 Gi Ceph block PVC for app state, and a 500 Gi NFS RWX volume for the ROM library on TrueNAS.

**Architecture:** Two-controller HelmRelease (`romm` + `valkey`) using bjw-s app-template, plus a separate CNPG `Cluster` resource and a `ScheduledBackup`. The ROM library lives on a manually-defined NFS PV (matching the immich-library precedent). VolSync handles daily backup of the small Ceph PVC; CNPG handles weekly volumeSnapshot of the postgres data PVC. Internal-gateway only — no Tailscale, no Cloudflare.

**Tech Stack:** Flux (OCIRepository + Kustomization), bjw-s `app-template` 4.6.2, RomM 4.8.1 (`docker.io/rommapp/romm:4.8.1`), Valkey 9.0.3, CloudNative-PG 1.X (operator already installed), PostgreSQL 16, External Secrets + 1Password, VolSync + Kopia, Cilium NetworkPolicies, Gateway API HTTPRoute via `envoy-internal`.

**Spec:** `docs/superpowers/specs/2026-04-30-romm-design.md`

## Pre-implementation manual prerequisites

Before pushing this plan's commits, the user must:

1. **Create the NFS share on TrueNAS**: dataset/folder `/mnt/HDD1X4/apps/romm/library`, exported via NFS, with subfolders `roms/`, `roms/<platform>/`, `bios/` as needed. Set `chown -R 1000:1000` on the tree.
2. **Create the IGDB app on Twitch Dev Portal** (https://dev.twitch.tv/console/apps): name `romm-homelab`, OAuth Redirect `http://localhost`, Category `Application Integration`. Note the **Client ID** and generate a **Client Secret**.
3. **Create the SteamGridDB API key** at https://www.steamgriddb.com/profile/preferences/api. Note the **API key**.
4. **Generate `ROMM_AUTH_SECRET_KEY`**: `openssl rand -hex 32` (64-char hex string).
5. **Create the 1Password item** in vault `default`, item name `romm`, with these six fields:
   - `ROMM_AUTH_USERNAME` — `admin`
   - `ROMM_AUTH_PASSWORD` — strong password (use 1P generator)
   - `ROMM_AUTH_SECRET_KEY` — the 64-char hex from step 4
   - `IGDB_CLIENT_ID` — from step 2
   - `IGDB_CLIENT_SECRET` — from step 2
   - `STEAMGRIDDB_API_KEY` — from step 3

These steps are out-of-band (1Password UI + TrueNAS UI + browser); they do NOT belong in any task below. The implementation can be pushed before all six fields exist in 1Password — the ExternalSecret will just retry until the source values appear.

This is the densest file. The structure follows two existing repo precedents jointly:
- **Multi-controller pattern**: `kubernetes/apps/selfhosted/paperless/app/helmrelease.yaml` (paperless + redis controllers)
- **Inline PVC + service.app.primary + advancedMounts**: `kubernetes/apps/games/crafty/app/helmrelease.yaml`

Note on the `route.app.rules[0].backendRefs[0].identifier`: the bjw-s app-template's `getByIdentifier` helper looks up the **service key** (here `app`), not the controller name. With `identifier: app` the rendered HTTPRoute correctly targets the auto-named Service `romm-app`. (This was a critical bug discovered in the Crafty rollout — `identifier: crafty` failed to render. Same trap avoided here.)

Notes the implementer should keep in mind while typing:

- `service.app.primary: true` makes the bjw-s chart pick `app` as the default service for the rendered HTTPRoute, but it does **not** change the produced Service name — services will be named `romm-app` (port 8080) and `romm-valkey` (port 6379) per `<release>-<key>` convention with itemCount > 1 (verified against the Crafty deploy which shows `crafty-app` + `crafty-minecraft`).
- `persistence.data` (type: persistentVolumeClaim) is the only PVC-creating entry — `library` is `existingClaim`, doesn't count. With itemCount = 1, the rendered PVC name is just `romm` (chart fullname), **not** `romm-data`. Confirm at first reconcile by `kubectl -n games get pvc`.
- `valkey-tmp` emptyDir uses `subPath` per mount to isolate `/tmp` and `/data` into separate subtrees of the same volume (lesson from Crafty's `nginx-tmp` review).
- The `&romm_probe`/`&valkey_probe` YAML anchors share the liveness spec into readiness — same pattern used by `actual-budget`.
- Renovate annotations at the top of each `image:` block (no auto-merge for now; flip to minor+patch auto-merge after a few months of RomM stability).
